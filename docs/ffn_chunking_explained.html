FFN Chunking, visually explained

The GitHub repo ComfyUI_LTX-2_VRAM_Memory_Management exposes a family of techniques for squeezing long-video LTX-2 renders onto modest GPUs. The core idea — the one that applies to your single-H100 deploy — is called Chunked FeedForward (or FFN chunking). This page explains what it is, why it works mathematically, how much memory it saves, and where it fits on top of your existing FA3 + TeaCache + temporal-windowing stack.

Status note: The repo's author updated their README on 2026-01-24 to say that Kijai's ComfyUI-KJNodes now ships an equivalent FFN chunking node, and ComfyUI nightly's memory manager made their custom nodes redundant inside ComfyUI. The technique is still valid and is what this page is about — but if you ever cross-check against the repo itself, know that it's been community-superseded for ComfyUI users. Your stack isn't ComfyUI-based, so the technique still needs to be hand-ported.

1. Where the memory actually goes

Every transformer block has two big submodules: self-attention and feed-forward network (FFN). Attention gets most of the research attention (FlashAttention, FA3, ring attention, etc.), so you already have FA3 handling that part. But the FFN has its own memory personality, and on long sequences it can be the larger peak.

The FFN is just two linear layers with a nonlinearity between them:

FFN(x) = (GELU(x · W1)) · W2
         └──── expands 4× ────┘

The first matmul takes (B, S, D) → (B, S, 4D). That 4×-expanded tensor in the middle is what eats VRAM. You then contract back to (B, S, D) for the output.

LTX-2 runs this FFN roughly 96 times (48 transformer blocks × 2 FFNs per block in some configs, or 1 per block across both stages). Each invocation transiently materialises the 4D intermediate. The GPU doesn't hold all 96 at once — only one is live at a time — but that one is the per-layer ceiling, and it grows linearly with sequence length S.

2. Why sequence length S is the problem for long videos

S is the token count — how many "patches" the video compresses into. In LTX-2, that's roughly frames × spatial_tokens_per_frame. Stage 2 is where it hurts, because the spatial resolution is high:

The red line is the unchunked status quo: as frames grow, S grows, and so does the 4×-expanded intermediate. The green dashed line is chunked FFN: peak memory is independent of sequence length, because you only ever materialise one small chunk's worth of the intermediate at a time.

3. The insight: FFN is pointwise

Here's why chunking is safe. In attention, each output token depends on every other input token (that's the whole point of attention). You can't naively split attention across the sequence because the cross-token dependencies would be lost.

The FFN is different. For every token position i, the output only depends on the input at that same position: 

yi = (GELU(xi · W1)) · W2    ← depends only on xi

No token talks to any other token inside the FFN. That means you can split the sequence into chunks, run the FFN on each chunk independently, and concatenate the results — the math is bitwise identical to running it all at once. No approximation, no quality loss, no precision fuzz.

4. The trick, visually

Instead of feeding the whole sequence through the FFN and materialising the huge (B, S, 4D) intermediate, you feed it one slice at a time, reuse the output buffer, and the peak only has to hold (B, chunk_size, 4D).

chunk 1 chunk 2 chunk 3 chunk 4 FFN intermediate (4×)

In code, it's surprisingly small

# Before
def forward(self, x):
    return self.w2(gelu(self.w1(x)))        # materialises (B, S, 4D)

# After — the whole optimisation
def forward(self, x):
    out = torch.empty_like(x)
    for i in range(0, x.shape[1], chunk):
        out[:, i:i+chunk] = self.w2(gelu(self.w1(x[:, i:i+chunk])))
    return out

That's it. No special kernels, no custom CUDA, no gradient acrobatics, no approximations. It's a for-loop wrapped around the existing matmuls. The ~8× memory reduction the repo claims is simply the ratio of full-sequence to per-chunk intermediate size.

Your docs/VRAM_MAP.md already has this technique logged as Lever #4 ("FFN chunking on Stage 2 forward", ~1–2 GB saved, +2–5% latency, low risk). Here's why the savings are smaller for you than the repo's ~8× claim:

FA3 dominates the non-FFN transient A lot of your Stage 2 transient is attention buffers + RoPE split; FFN is a minority share.

The repo saw 8× because they start from a no-windowing, no-FA3, single-24 GB-4090 baseline where the FFN intermediate really is the peak. On your pod, you're already past the cliff — FFN chunking is a "top-off" optimisation, not a door-opener.

Same consumer-grade GPU, same model, same quality — just chunked. That's the visible benefit for long videos: you stop being VRAM-gated and start being wall-clock-gated.

For your H100 deploy, the equivalent would be: temporal windowing + FFN chunking + FA3 + TeaCache unlocks 20 s+ renders on the same 80 GB pod without moving off the H100 class. Each lever individually buys a few GB; stacked, they compound.

7. The trade-offs, honestly

What you give up

  • Latency: +2–5%. More kernel launches, less matmul fusion opportunity.
  • Chunk-size tuning. Too small = kernel overhead dominates. 256–512 tokens is the sweet spot for most LTX-2 configs.
  • Training unclear. The repo hypothesises gradient-accumulation errors could drift — ignore this, you're inference-only.

What stays the same

  • Output quality. Mathematically exact — same bytes, same pixels.
  • Weights / checkpoint. No fine-tuning, no re-export.
  • Framework. Pure PyTorch nn.Module wrapper — no custom kernels, no triton, no C++.
  • Attention path. FA3 keeps doing its thing; this only touches the MLP.

8. The repo's fancier variants (context only — not for your single-H100 stack)

Same repo ships three multi-GPU variants. None of these apply to a single-H100 deploy, but they're worth understanding so you know what to reach for if you ever horizontally scale.

VariantProblem solvedWhen you'd use it
V3: FFN chunking
applies to you		 FFN intermediate too big for one GPU Any single-GPU deploy. This is the one you care about.
V2: Tensor parallelism Shard FFN/attn across GPUs with Megatron-style all-reduce 2+ GPUs on fast interconnect; faster, not just bigger.
Multi-GPU Chunked ("process once, immediately offload") Stage 2's 17 GB timestep tensor doesn't fit on one GPU — build it, instantly slice it across N storage GPUs 3+ GPUs, extreme sequence lengths (900+ frames @ 1080p).
V5: Ring Attention + Sequence Parallelism Sequence itself is too long for any one GPU — split tokens across N GPUs, rotate K/V around the ring 7×4090-class rigs chasing 600K+ tokens. This is the most advanced option and overkill for your stack.

For context: ring attention is how you'd solve the attention problem if chunking the FFN still left you OOM. It doesn't touch the FFN; it touches attention. The two techniques are complementary — on a multi-GPU deploy you'd use both.

9. Practical takeaway for this project

Should you implement FFN chunking on your H100 deploy?

Probably not yet. Your VRAM_MAP.md has the right prioritisation:

  1. Land Stage 2 temporal windowing first. That's the 24 GB save that closes the 10 s OOM.
  2. Re-measure. Confirm Stage 2 peak drops below ~75 GB.
  3. Then, if you're pushing 15 s / 20 s renders and need another 1–3 GB, add FFN chunking. It's a ~20-line nn.Module wrapper around FeedForward in the LTX-2 transformer.

The technique is low-risk, low-complexity, and fully reversible (set ffn_chunks=1 to disable). When you implement, apply it only on Stage 2's transformer blocks — Stage 1's transient is already negligible per your measurements, so the latency cost there buys nothing.

Reference: the repo has the exact wrapper pattern at comfyui_tensor_parallel_v3/ — strip out the ComfyUI glue and you have a drop-in ChunkedFeedForward(nn.Module).
