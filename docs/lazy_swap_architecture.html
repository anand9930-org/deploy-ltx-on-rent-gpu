What's happening when you alternate I2V ↔ T2V

Short version: quality is identical, but you pay a one-time ~145 s "rebuild tax" each time you switch modes. No model degradation, no cumulative loss — just a wall-clock penalty that disappears once the same mode is reused.

To answer the question first: there is no quality loss from alternating. Each mode rebuilds from disk to a clean state, and the seed-→ output mapping is deterministic. The cost is purely time, not fidelity. Pixel output of "I2V then T2V" is bit-identical to "T2V from a fresh boot" at the same seed.

Add to that: FP8 mode requires OffloadMode.NONE (so the GPU has the kernels needed for cuBLAS scaled-mm to work without paging), which means we can't stream weights to CPU as a fallback. The choice is binary — either one pipeline is GPU-resident, or neither is.

2. The "lazy swap" mechanism

So the wrapper holds at most one upstream pipeline alive. When a request needs the other one, it does this in sequence:

  1. teardown del self._pipeline; gc.collect(); torch.cuda.empty_cache() — drops every reference, returns the ~30 GB DiT + scratch buffers to the allocator pool.
  2. disk I/O Reads the new safetensors files (~30–60 GB) from local NVMe. Page cache is pre-warmed at boot, so this is RAM→GPU not disk→GPU — but it's still ~30 GB of bytes to memcpy.
  3. FP8 probe Reopens the safetensors header and walks every .weight key to find which transformer modules need to stay BF16 (they're excluded from FP8 quantization). One-shot per checkpoint, but it runs on every rebuild because the policy is built fresh.
  4. construct Builds the DiffusionStage objects, applies the FP8 quantization policy, fuses any LoRAs, installs the audit hooks.
  5. ready Active mode flag flips, request runs.

Total elapsed: 30–60 s on a freshly booted pod, ~145 s in your session (slower because the alternative pipeline's pages had already been evicted from page cache by the previous I2V's working set).

4. Why T2V is intrinsically slower than I2V even without the swap

Factor I2V (unified) T2V (two-stage) Cost ratio
Inference steps ~8 (LCM-distilled) 30 (proven fp8-h100 config) 3.75×
Forward passes per step 1 (SimpleDenoiser) 3 (cond + uncond + STG-perturbed) 3×
Latent grid (your run) 1280×1920 ≈ 2.46 M px 1024×1536 ≈ 1.57 M px 0.64× (smaller, helps T2V)
Net per-frame compute baseline 3.75 × 3 × 0.64 ≈ 7.2× ~7× more

The 30 steps + CFG/STG aren't waste — they're what gives T2V its motion fidelity and prompt adherence on novel scenes. I2V doesn't need the extra guidance because the input image already constrains the output.

5. Mitigations (in order of practical value)

Batch by mode if you can

Group all your I2V calls together, then all your T2V calls. You pay the ~145 s tax once per group instead of every request. Five I2Vs back-to-back save ~580 s vs alternating.

Pick the right boot default

Set LTX_DEFAULT_MODE=i2v on pods that mostly serve I2V (e.g. avatar workflows). The first request lands warm; only the rare T2V pays the swap.

Run two pods, one per mode

For mixed traffic where alternation is unavoidable, two H100 pods (one with LTX_DEFAULT_MODE=t2v, one with =i2v) eliminate the swap entirely. Each pod sees only same-mode traffic. ~$6/hr instead of $3/hr, but no swap penalty ever.

Wait for H200 (141 GB)

Both pipelines fit resident on H200 with ~10 GB headroom. No swap, no rebuild. Today's H100 cost is the constraint, not the architecture.

6. The bottom line

Nothing degrades with alternation. The pipeline rebuild is byte-exact: same weights, same FP8 policy, same kernels. The only thing you "lose" by alternating is wall-clock seconds. The first request after a mode change costs +30–145 s; every follow-up in the same mode is at full speed.

If your workload is steady state in one mode, you'll never see the penalty after the first warm-up. If it's truly mixed, the cheapest mitigation is to batch by mode at the application layer; the most thorough is two pods.
