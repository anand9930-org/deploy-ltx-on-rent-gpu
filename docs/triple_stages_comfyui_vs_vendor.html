Triple-Stage Pipeline Comparison

A side  ComfyUI workflow   scripts/workflow_3mljpp.py — auto-generated from 3mljpp-api.json by pydn/ComfyUI-to-Python-Extension (876 lines).
B side  Vendor pipeline   src/vendor/ti2vid_triple_stages.py — class-based pipeline atop ltx_pipelines (438 lines).
Both produce a 3-stage LTX-2.3 22B audio-video output. The vendor file was authored "based on the ComfyUI three-stage workflow" (per its docstring).

TL;DR — they are not equivalent

Both files describe a three-stage diffusion flow with shared building blocks (text/image conditioning, sampling, latent upsampling, AV decode), but they differ on five load-bearing axes:

  1. Number of latent upsamples: ComfyUI does two (Stage 1→2 and 2→3, total 4× spatial). Vendor does one (Stage 1→2, total 2× spatial). Stages 2 and 3 in the vendor run at the same resolution.
  2. Distilled-LoRA scope: ComfyUI applies the distilled LoRA to all three stages (one shared LoraLoaderModelOnly). Vendor applies it to Stage 3 only.
  3. Image preprocessing: ComfyUI runs LTXVPreprocess(img_compression=18) on the conditioning image before Stage 1; Stages 2/3 use the raw resized image. Vendor passes preprocessed_images=None for every stage.
  4. Sigma schedule and step counts: ComfyUI uses three hand-authored sigma lists (8/3/3 steps). Vendor uses the project's LTX2Scheduler with default 16/8/8 steps — the docstring acknowledges this is more steps than the source workflow.
  5. Stage 3 initial state: vendor's Stage 3 omits initial_latent for both video and audio. Likely bug: DiffusionStage.__call__ falls back to creating noise from scratch, so Stage 3 cannot refine the Stage-2 result the way the ComfyUI workflow does.

Major divergences

1 · Vendor Stage 3 likely starts from pure noise

In blocks.py:
_build_state(spec, ...) calls create_noised_state(initial_latent=spec.initial_latent, noise_scale=spec.noise_scale). When spec.initial_latent is None (vendor Stage 3 for both video and audio), the state is built from a fresh Gaussian noise tensor — Stage 2's output is dropped on the floor.

Compare: 

// vendor stage 2 (correct refinement pattern)
video=ModalitySpec(
    context=v_context_p,
    conditionings=stage_2_conditionings,
    noise_scale=stage_2_sigmas[0].item(),
    initial_latent=upscaled_video_latent,
)

// vendor stage 3 (no carry-through)
video=ModalitySpec(
    context=v_context_p,
    conditionings=stage_2_conditionings,
    # no initial_latent, no noise_scale
)

The ComfyUI workflow's Stage 3, in contrast, takes the upsampled Stage-2 latent as latent_image for SamplerCustomAdvanced and re-noises it from σ[0]=0.85 — a textbook refinement pass. The vendor docstring describes Stage 3 as "another full-resolution refinement pass" but the implementation does not refine; it generates from scratch with the same prompts and 8 Karras-style steps.

The fix is one line per modality — pass initial_latent=video_state.latent and the audio equivalent, plus noise_scale=stage_2_sigmas[0].item(), to make the vendor's Stage 3 mirror the ComfyUI semantics. Worth confirming with whoever authored the file before editing — there may be a deliberate intent that I'm missing.

2 · Vendor performs only one latent upsample

The ComfyUI workflow chains two LTXVLatentUpsampler calls (×2 → ×2 = ×4 spatial). Stage 1 generates at ~7×10 latent dims; the final decoded video is at ~28×40 latent dims (≈896×1280 px).

The vendor pipeline upsamples once (Stage 1 → Stage 2). Stage 2 and Stage 3 share the same resolution. With default args (--width 1536 --height 1024), Stage 1 runs at 768×512 and Stages 2–3 at 1536×1024 — only a 2× spatial increase.

These produce different artifacts: ComfyUI uses Stage-3 not just to refine but to push spatial detail further; the vendor file uses Stage-3 purely as a refinement (or, given the bug above, as a generation pass at full res).

3 · Distilled LoRA scope is inverted

Project convention (per packages/ltx-pipelines/CLAUDE.md):

  • Two-stage pipelines: distilled LoRA on Stage 2 only.
  • HQ pipeline: distilled LoRA on both stages, with separate strengths.

The triple-stage vendor places it on Stage 3 only, while the ComfyUI workflow loads it once at the top and applies it to all three stages. If the design intent was "distilled LoRA polishes the final pass", the vendor matches that intent; if the intent was "use distilled LoRA throughout to keep step count low", the vendor doesn't.

4 · Image preprocessing is asymmetric in ComfyUI, absent in vendor

The ComfyUI workflow runs LTXVPreprocess(img_compression=18) on the conditioning image only at Stage 1. Stages 2 and 3 use the resized image directly. The H.264-style compression at the lowest-resolution stage is a deliberate technique: the model learns to lift quality stage-by-stage, so feeding a degraded image at the start lets it commit to coarse structure without over-fitting to high-frequency artifacts.

The vendor pipeline passes preprocessed_images=None to every combined_image_conditionings call — there is no analog of this stage-1-only degradation. The docstring mentions "no H.264 preprocessing" as an intentional simplification.

5 · Sampler family differs (ancestral vs non-ancestral)

ComfyUI Stage 1 uses euler_ancestral_cfg_pp — ancestral sampling re-injects noise at every step, raising stochasticity (and seed sensitivity). Stages 2 and 3 use euler_cfg_pp (no ancestral noise).

The vendor pipeline goes through EulerDiffusionStep + euler_denoising_loop for all three stages — non-ancestral. The single GaussianNoiser is reused across stages; multiplying step count by 2× (16 vs 8) compensates partly for the loss of ancestral diversity, but the runs are not directly comparable.

Code structure

workflow_3mljpp.py
  • Lines 1–180: ComfyUI bootstrap (sys.path, server stub, custom node import, allocator env).
  • Lines 183–548: build_workflow() — the API JSON re-emitted as a Python dict; passed back into SaveVideo as prompt metadata.
  • Lines 555–558: module-level statements — workflow, prompt, extra_pnginfo evaluated at import time.
  • Lines 561–871: main(unload_models) — the only execution path. for q in range(1) wraps everything (the --queue_size argument); each iteration randomizes the three RandomNoise seeds.
  • Hard-coded everywhere: image filename, prompts, frame count, sigma values, dimensions. To change inputs, edit the dict in build_workflow() or feed a different JSON to the converter.
ti2vid_triple_stages.py
  • Lines 22–51: imports from ltx_core / ltx_pipelines. All upstream symbols normally land via src/upstream.py; this file imports directly because it lives in src/vendor/ (a vendored, lightly-edited copy from the upstream repo).
  • Lines 54–117: TI2VidTripleStagesPipeline.__init__ — declarative ownership of every model component, with three DiffusionStage instances differing only in their loras tuple.
  • Lines 119–278: __call__ — the actual pipeline. Six logical steps (prompt encode → stage 1 → upsample → stage 2 → stage 3 → decode), one assertion, no branching.
  • Lines 281–341: build_arg_parser — every knob is an explicit CLI flag with a default and a docstring.
  • Lines 344–438: main — argparse plumbing into the pipeline call + encode_video at the end.
  • Knobs that don't exist in the ComfyUI side: --quantization {fp8-cast, fp8-scaled-mm}, --compile, --streaming-prefetch-count, --max-batch-size. The pipeline is wired into the BentoML service through these.

If you wanted byte-equivalent output

The two pipelines are built to different goals — ComfyUI's flow is one specific run, the vendor's is a parameterized library. Even so, here's the minimum diff if you wanted the vendor file to reproduce the ComfyUI workflow's exact behavior:

  1. Add a second VideoUpsampler step between Stage 2 and Stage 3, and pass the result as initial_latent to Stage 3.
  2. Pass initial_latent=upscaled_stage2 + noise_scale=stage_2_sigmas[0].item() to Stage 3's video ModalitySpec (and the audio analog). This fixes the implementation regardless of whether the second upsample is added.
  3. Add a preprocessed_images code path so Stage 1 can consume an H.264-degraded image (mirror LTXVPreprocess(img_compression=18)). Stages 2 and 3 keep the raw image.
  4. Apply distilled LoRA to Stages 1 and 2 as well (or, equivalently, drop it from Stage 3 and load it as part of loras at construction).
  5. Allow injecting hand-authored sigma tensors per stage (the existing LTX2Scheduler.execute(steps=N) path is fine for production but not bit-for-bit equivalent).
  6. Use ancestral Euler for Stage 1 only — currently no path through DiffusionStage exposes the stepper override from the public __call__ signature, so this requires a small plumbing change.
